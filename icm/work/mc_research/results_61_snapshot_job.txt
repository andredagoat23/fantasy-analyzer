Contracts (all demonstrated in section 3):
  IMMUTABLE   — writes to data/snapshots/YYYY-MM-DD/; a dated dir containing MANIFEST.json is
                finished and the script REFUSES to touch it (exit 1). A dated dir without a
                manifest is a crashed run: rerunning the same day resumes it, never overwriting
                existing files, and writes the manifest last as the commit marker.
  FAIL-SAFE   — every source fetches independently inside its own try/except; one source down
                cannot kill the others. Hard content asserts (FFC >100 players + non-null
                total_drafts; kona >300 ADP rows; Sleeper universe >5000 + >200 adp_ppr; FP
                ecr/sd/best/worst columns + >300 ppr rows; depth charts dt schema + >1000 rows)
                make a hollow response FAIL LOUDLY into the manifest instead of silently writing
                a 5-row file — the exact failure mode that poisoned the panel's 2025 prices
                (48_ [R]: the FantasyPros 5-row preview became adp values 1.0–5.0).
  MANIFEST    — MANIFEST.json per snapshot dir records, per source: ok, file, rows, bytes,
                seconds, fetched_at_utc, error, and source-specific notes (drafts counted, scrape
                dates and staleness, injury-status mixes, missing columns). Plus snapshot-level:
                phase, completed_week, week_source, total_seconds, total_bytes.
  S8-AWARE    — every nflreadpy frame is slimmed by INTERSECTION with an expected column list;
                a schema change degrades to a "missing_cols" entry in the manifest, not a crash.
                nflreadpy cache mode is forced to "memory" so a snapshot can never silently serve
                last week's disk cache as today's data.
  WEEK LOGIC  — completed_week = highest REG week whose games all predate today, from the live
                schedule; if the schedules source is down, a date-arithmetic fallback anchored on
                the 2026 week-1 final gameday (Mon 2026-09-14, read from the live schedule [V])
                keeps the in-season block alive; manifest records which source decided the week.

COMMIT POLICY (JUDGMENT, recommended): data/snapshots is NOT in .gitignore [V] — snapshots commit

must not delete the season. ~90 MB/season is acceptable repo weight for the programme's

to external backup — do NOT stop capturing them.

5. CADENCE RECOMMENDATION: TUESDAY, SEASON-ROUND (+ ONE EXTRA RUN ON DRAFT MORNING)
========================================================================================
Run every TUESDAY (afternoon/evening ET), all year. Reasoning, labelled:

  MEASURED [V]: NFL weeks close with Monday Night Football — every 2026 week's final game is a
  Monday (regular weeks; occasional late-season Saturday closers only make Tuesday safer).
  JUDGMENT (standard publication/league practice, verifiable in the first two in-season
  snapshots): (a) nflverse's automated pipelines land the completed week's snap counts /
  participation / injuries by Tuesday morning after MNF; (b) ESPN league waivers process
  overnight Tuesday-into-Wednesday, so Wednesday-morning rosters already reflect claims;
  (c) team practice/injury reports for the NEXT week begin Wednesday and finalize Friday.

  Therefore Tuesday is the unique day that captures, in one shot:
    - the completed week W's usage data, complete (after MNF, after the nflverse refresh),
    - BEFORE Wednesday waivers — i.e. exactly the information set available at the week's
      waiver/lineup decision, which is what WS3's lineup-timing rule requires ("a detection made
      after Week W may only affect Week W+1's lineup, and no waiver claim may resolve before the
      W+1 processing date"),
    - BEFORE any of week W+1's practice reports exist — so the snapshot cannot leak the coming
      week's injury news into a lead-time claim (S7's shape).
  A Wednesday run would contaminate the price series with post-waiver moves and W+1 practice
  reports; a Monday run misses MNF. Tuesday is not a preference, it is the seam between the two
  information regimes.

  SELF-CHECK PROTOCOL (falsifiable, pre-stated): each in-season manifest records the weeks
  present per source. If the just-completed week W is ABSENT from a Tuesday snapshot's
  injuries/snap_counts/participation notes twice in the first three in-season weeks, the nflverse
  Tuesday-refresh assumption is wrong for 2026 — move the cadence to Wednesday 06:00 ET (still
  pre-waivers in this league) and record the change in this file. The manifest makes the check a
  10-second read.

  EXTRA RUN, DRAFT MORNING (Fri 2026-08-07): the §9.1 pre-registration requires every named-player
  call to be stated "relative to a RECORDED price, with the ADP snapshot file written down." The
  2026-08-07 snapshot dir IS that file. Run the tool once before the draft; the regular Tuesday
  Aug 4 run does not substitute (three days of ADP drift on the platform the league drafts on).

  OPTIONAL, NOT MANDATED (JUDGMENT): a second weekly capture on Friday would record the final
  practice designations that shape the start/sit decision. Valuable for a future start/sit study;
  NOT required by any current workstream — do not let it dilute the one non-negotiable cadence.
  The tool supports it as-is (dirs are dated by day).

  PRESEASON (now -> Sep): same Tuesday cadence. ADP/ECR/depth charts drift daily through August;
  the weekly series plus the draft-morning capture is the price record. First scheduled runs:
  Aug 4, Aug 7 (draft morning), Aug 11, 18, 25, Sep 1, Sep 8; first in-season snapshot Tue Sep 15
  (week 1 completes Mon Sep 14).

  Nothing is automated by this task (no cron/launchd installed — that is a user decision about
  their machine; the command is one line: .venv/bin/python tools/weekly_snapshot.py). Until
  automated, a repeating Tuesday calendar reminder is the honest minimum. Committing + pushing
  the new dir after each run is part of the ritual — an unpushed snapshot is one disk failure
  away from not existing.

7. LIMITATIONS AND WHAT WAS NOT DONE (say it plainly)
========================================================================================
  * The 2026 in-season path has NOT run against 2026 — it cannot before week 1. It was exercised
    against 2025 end-to-end (section 3). Residual risk: nflverse may lag publishing 2026
    participation early in the season (2025 had a full file, but availability in week 1 of a new
    season is not guaranteed); the fail-safe design records a miss rather than dying, and the
    self-check protocol in section 5 covers the cadence consequence.
  * NGS and pbp weekly captures are NOT included — the assignment scoped the in-season pull to
    injuries/snap-counts/participation (charter §9.2 also names NGS/pbp). Cost to add later: one
    ~15-line fetcher each in the established pattern (~100 KB/season-to-date for NGS; pbp slimmed
    to 46_'s 23 columns ~175 KB). Recommend adding NGS before Week 1 if WS3 wants separation/
    air-yards metrics in the lead-time record; pbp is lower priority (its revisions are partially
    recoverable from nflverse release history, unlike prices, which vanish).
  * ESPN kona ignores the X-Fantasy-Filter limit/sort in this view (returns the full 11,515-row
    active set regardless) [V]. Harmless — the position filter reduces to 4,506 — but worth
    knowing: the filter is decoration, not pagination.
  * ESPN appliedTotal is served for only 33 players [V]; per-player component stats (462 players)
    are the durable projection record — same convention as tools/archive_projections.py.
  * A source that fails on snapshot day stays failed for that date (the dir seals with its
    manifest). Deliberate: a retriable snapshot is a mutable snapshot. The outage record is data.
  * Same-day partial reruns are supported ONLY for a crashed run (no manifest yet): existing
    files are kept, missing ones fetched. Once the manifest exists the date is closed.
  * Sleeper 2026 adp_ppr currently carries only 245 non-sentinel values [V] — thin early-market
    depth, matching FFC's 247; expect both to deepen through August. The manifest tracks it.
  * No hypothesis was tested and no points number is claimed anywhere in this task (S14: n/a).
